# Хранилище вложений — настройка для заказчика

Блоки между маркерами `generated:*` генерирует `kit/build_help.py render-storage` из реестра `kit/install-steps.yaml` —
руками их не правят: правка реестра плюс перегенерация. Команды ниже запускаются из корня вашего репозитория.

## Зачем это нужно

К записям трекера можно прикладывать файлы — снимки экрана, документы, видео. Файл до порога размера ложится прямо в
git, рядом с записью. Файл крупнее порога в git не кладётся: он уходит в ваше собственное S3-совместимое хранилище, а
по тому же пути в репозитории остаётся маленький текстовый указатель с контрольной суммой. Ссылка в тексте записи от
этого не меняется.

Хранилище и ключи доступа — ваши. Комплект хранит в git только имена переменных окружения, а не значения ключей. Байты
идут от бота прямо в ваш бакет; вендор комплекта их не видит и через себя не пропускает.

Хранилище подключать не обязательно. Без него файлы до порога ложатся в git, а на каждый файл крупнее бот отвечает
отправителю «не сохранено — хранилище не настроено». Ссылка в тексте записи при этом остаётся.

## Выбор провайдера

Подойдёт любое S3-совместимое хранилище:

| провайдер | эндпоинт | регион |
|---|---|---|
| Yandex Object Storage | `https://storage.yandexcloud.net` | `ru-central1` |
| AWS S3 | `https://s3.<регион>.amazonaws.com` | регион бакета, например `eu-central-1` |
| Cloudflare R2 | `https://<account-id>.r2.cloudflarestorage.com` | `auto` |
| MinIO (свой сервер) | адрес вашего сервера, только `https://` | как настроен сервер |

Если вы работаете из России и во вложениях будут персональные данные граждан РФ, закон требует хранить их в базах данных
на территории РФ (152-ФЗ, ст. 18 ч. 5). Подходит ли вам конкретный провайдер, решает юрист — проконсультируйтесь с ним.

## Бакет

Создайте у провайдера отдельный бакет для вложений:

- **приватный**: без анонимного чтения и листинга, без публичных ACL и публичных ссылок;
- **без версионирования**. Изъятие файла (например, если в него попал секрет) обязано удалять байты, а не прятать их за
  старой версией объекта;
- больше в бакете ничего не храните — так проще проверить, что лежит внутри.

## Ключи доступа

Ключей несколько, и у каждого своя роль.

- **Ключ писателя** — отдельный сервисный аккаунт с правами только на загрузку, чтение и проверку объекта (put, get,
  head) в этом бакете. Права на удаление (delete) и листинг (list) у него быть не должно. В Yandex Object Storage и AWS это
  удобнее всего задать политикой доступа бакета: разрешить аккаунту только `PutObject` и `GetObject` (проверка объекта
  входит в `GetObject`).
- **Отдельный ключ на каждого потребителя.** У бота в CI и у бота-демона на вашем сервере — разные ключи с одинаковыми
  правами писателя. Утёкший ключ одного потребителя вы отзываете, не останавливая другого.
- **Ключ изъятия** — отдельный, с правом удаления объектов. Его держит человек, который отвечает за изъятие. Боту он не
  нужен и в секреты CI не кладётся.

Значения ключа писателя кладутся только в два места:

- в секреты CI репозитория, под именами из реестра комплекта (ниже);
- в файл окружения демона `.env.workshop` рядом с docker-compose, с правами 600, если бот у вас работает демоном.

Имена секретов ключа писателя (сгенерировано из реестра kit/install-steps.yaml):

- `WORKSHOP_S3_ACCESS_KEY_ID` — идентификатор статического ключа ПИСАТЕЛЯ S3-совместимого хранилища вложений (права put/get/head на один бакет, без list и delete)
- `WORKSHOP_S3_SECRET_ACCESS_KEY` — секрет того же ключа писателя хранилища вложений

Никогда не кладите значения ключей в git, в файлы конфига и в чат — ни целиком, ни частью.

## Файл `.workshop/storage.yaml`

Комплект кладёт этот файл при установке как шаблон с закомментированным примером. Раскомментируйте блок `storage` и
впишите эндпоинт, регион и бакет:

```yaml
storage:
  endpoint: https://storage.yandexcloud.net
  region: ru-central1
  bucket: my-workshop-attachments
  addressing: path
```

Необязательные строки:

- `git_threshold_bytes` — порог git на верхнем уровне файла (не внутри `storage`);
- `addressing` — `path` (по умолчанию) или `virtual`;
- `timeout_s` и `deadline_s` — целые секунды;
- `list_permission: true` — только если у ключа писателя всё же есть листинг.

Затем запустите:

```
python3 .workshop/bot/kit/install.py storage-init
```

`storage-init` допишет в блок три факта: `credentials`, `key_prefix` и `canary_key`. Ваши строки и комментарии он не
трогает. В `credentials` — имена секретов из реестра комплекта, значения ключей в файл не попадают:

<!-- generated:storage-credentials:start -->
```yaml
  credentials:
    access_key_id: WORKSHOP_S3_ACCESS_KEY_ID
    secret_access_key: WORKSHOP_S3_SECRET_ACCESS_KEY
```
<!-- generated:storage-credentials:end -->

Кроме имён секретов, он допишет:

- `key_prefix` — случайный префикс ключей объектов. Он создаётся ОДИН раз и на экран не печатается. Префикс прячет
  объекты от постороннего: не зная его, нельзя проверить, лежит ли в бакете файл с известным содержимым;
- `canary_key` — имя маленького проверочного объекта под префиксом. По нему проба проверяет ключ писателя.

**Префикс не меняйте.** Новый префикс означает новое хранилище: все уже сохранённые вложения станут недоступны.
Если файл конфига потерян, `storage-init` найдёт прежний префикс в истории git и откажется создавать новый.
Сознательная смена хранилища — отдельная процедура: скопировать объекты под новый префикс, проверить их, только потом
переключать конфиг.

После `storage-init` закоммитьте `.workshop/storage.yaml`: бот в CI читает конфиг из репозитория.

## Проверка

```
python3 .workshop/bot/kit/install.py storage-status
python3 .workshop/bot/attach --json status --verify
```

`storage-status` проверяет файл конфига, наличие ключей в окружении и делает пробу: читает проверочный объект ключом
писателя. `status --verify` дополнительно считает указатели в репозитории по состояниям и проверяет каждый сохранённый
объект: скачивает его и сверяет размер и контрольную сумму у себя.

Исход пробы (`storage_probe_outcome`):

| исход | что значит | что делать |
|---|---|---|
| `ok` | ключ писателя принят, проверочный объект читается | ничего |
| `storage-denied` | ключ отвергнут или проверочного объекта нет | проверьте значения ключа и права аккаунта; если объекта нет — запустите `storage-init` |
| `storage-unavailable` | сеть, таймаут, ошибка хранилища 5xx или бакета нет | проверьте эндпоинт, имя бакета и доступность; повтор может помочь |
| пусто | хранилище не настроено или значений ключа нет в окружении | см. подсказку в выводе: блок `storage` или секреты |

Сбои проверки в `status --verify` (`last_verification_failures`):

- `object-missing` — указатель есть, объекта в хранилище нет;
- `size-mismatch` — размер объекта не тот;
- `sha-mismatch` — размер тот, контрольная сумма не совпала.

Любой из них означает, что объект пропал или испорчен. Сверьте бакет; восстановите объект из резервной копии, если она
есть.

## Эксплуатация

### Порог git

Порог — строка `git_threshold_bytes` в `.workshop/storage.yaml`, целое число байт. По умолчанию — 8 000 000 байт.
Файл ровно такого размера остаётся в git, файл крупнее уходит в хранилище. Держите порог ниже предела размера файла
у вашего хостинга git (у GitHub — 100 МиБ). Смена порога действует только на новые файлы: уже записанные никуда не
переезжают.

### Что видит пользователь при «не сохранено»

Если файл сохранить не удалось, ссылка на него в тексте записи всё равно остаётся. В тексте нет пометки «не
сохранено»: после досохранения она стала бы неправдой. Бот отвечает на сообщение с каждым таким файлом отдельно,
одной из трёх пометок:

- «не сохранено — хранилище не настроено» — файл крупнее порога, а хранилище не подключено;
- «не сохранено — источник не отдал файл» — мессенджер не отдал файл боту (облачный Bot API не отдаёт файлы больше
  20 МБ);
- «не сохранено — загрузка не удалась» — хранилище отказало или недоступно.

Пока файл не сохранён, приложение показывает вместо него причину и ссылку на исходное сообщение.

### Изъятие файла

Если в файл попал секрет или человек просит удалить свои данные, файл изымают. Делает это человек со своим ключом
изъятия; у бота такого права нет.

```
export MY_WITHDRAW_KEY_ID=…        # значения — только в окружении вашей сессии
export MY_WITHDRAW_SECRET=…
python3 .workshop/bot/attach withdraw-key-set <путь к указателю> --reason secret \
    --withdraw-key-id-env MY_WITHDRAW_KEY_ID --withdraw-secret-env MY_WITHDRAW_SECRET --confirm-withdraw
```

- `--reason`: `secret` (секрет в файле) или `erasure` (удаление по требованию).
- В аргументах передаются ИМЕНА переменных окружения, а не значения. Имена ключа писателя из конфига сюда не
  подойдут — команда откажет.
- `withdraw-key-set` удаляет объект один раз и переводит в состояние «изъят» все указатели на эти же байты, даже если
  они в разных записях. Сначала команда проверяет весь набор и ничего не удаляет, если хоть один указатель непригоден.
- Для одного указателя есть `withdraw` с теми же флагами.
- Пути из поля `staged` вывода закоммитьте одним коммитом.

Ссылки в тексте записей остаются; приложение показывает вместо файла пометку об изъятии. Файл, который лежал прямо в
git (был меньше порога), из истории git так не удалить: для этого нужна перезапись истории.

### Пути в командах

У команды `write` с флагом `--json` два поля с путями:

- `path` — путь от каталога записи, ровно в той форме, в какой он стоит в ссылке в тексте (`attachments/<id записи>/<имя>`);
- `staged` — пути в файловой системе, которые нужно закоммитить.

Команды `read`, `verify`, `withdraw` и `key-paths` ждут путь в файловой системе — берите его из `staged`, а не из `path`.
